- 2026-07-29 Issue #83: hardened `charts/tatara-memory`'s cnpg postgres so the chart cannot reproduce the CNPG failures the platform keeps paging on, and made the storage contract a render-time error instead of an inherited default. FINDING FIRST: the chart set NOTHING under `postgres.cluster` except `initdb`, so it inherited cnpg/cluster 0.6.1's defaults - `storage.size: 8Gi`, **`walStorage.enabled: false`** (pg_wal back on the PGDATA volume, the exact 2026-07-05 fill that 503'd `/memories:bulk`, tatara-operator#238), and `postgresql.parameters: {}` (**no `max_slot_wal_keep_size`**, so one stuck or diverged standby's replication slot pins WAL until the volume fills - the tatara-helmfile#263 mechanism). Both defects were live in the chart even though the operator's Go builder had fixed both for the per-project stacks a month earlier. Now explicit: 3 instances, 20Gi PGDATA, a dedicated 10Gi WAL volume, `max_slot_wal_keep_size: 5120MB` - byte-for-byte what the operator renders for the healthiest live cluster (`mem-tatara-pg`, verified against the live Cluster CR). GUARD: new `tatara-memory.validatePostgres`, included from `configmap.yaml` (the one template that always renders), `fail`s the render when any of those four is unset, and additionally when `max_slot_wal_keep_size` exceeds HALF of `walStorage.size` - the operator derives exactly that ratio, and a 2Gi WAL volume whose slot cap already claimed 1Gi is what crashlooped both replicas on 2026-07-06. The comparison needs a size parser, so `tatara-memory.kib` converts k8s (Ki/Mi/Gi/Ti) and postgres (kB/MB/GB/TB) BINARY suffixes to KiB and deliberately REJECTS decimal SI (`10G`) rather than approximating a check whose whole job is exactness. 10 helm-unittest cases cover every branch. NON-OBVIOUS, worth knowing before trusting this chart: **the chart is not what deploys the platform's memory stacks.** `release.yml` says "image-only, operator-provisioned; no chart" and publishes only the image; tatara-helmfile has no `tatara-memory` release; the live `mem-<project>` stacks are built in Go by tatara-operator `internal/memory/pg.go`, which is why the chart's defects survived unnoticed and why `Chart.yaml` appVersion (0.4.0) has drifted from the deployed image (v0.4.4) - left as-is rather than guessed at. So this change has no live effect today; if a release of this chart is ever created, note that enabling `walStorage` relocates pg_wal and rolls the pods, and cnpg REJECTS shrinking or disabling it afterwards. NOT taken, still open on #83: the write path has no bounded retry across a CNPG failover, and `mapServiceError` has no transient branch for a raw postgres connectivity error (`connection refused` during a primary outage falls to `default` -> 500, not 503 + Retry-After) - both are app-code changes to a hot path, out of this chart-scoped change.

- 2026-06-23 Issue #48: gave the retrieval-quality eval a real ranking signal via a scored `/queries:data` path. Wired the previously-dormant `lightrag.QueryData` (`POST /query/data`) end to end: new `Service.QueryData` -> new route `POST /queries:data` (mirrors `/queries:describe`: same auth gate, `top_k` clamp, validation) -> eval `Client.Query` now POSTs `/queries:data`. **Confirmed the v1.4.16 `/query/data` wire shape against the upstream source** (HKUDS/LightRAG `v1.4.16` `query_routes.py`), pinning what the 2026-05-27 OpenAPI inspection left unrecorded: `data = {entities, relationships, chunks, references}`; each `chunks[]` is `{content, file_path, chunk_id, reference_id}` and carries **no per-chunk relevance/score/similarity/rank field** (only `relationships[].weight`, a graph edge weight, exists). So the 2026-05-27 "Score cannot be populated" decision still holds at the field level. The win is that `/query/data` returns individual chunks **in retrieval order** (vs `/query`'s deduplicated reference pointers in arrival order), so `translate.go:queryResultFromChunks` derives `QueryMatch.Score = 1/(rank+1)` from that order - a deterministic, strictly-descending signal. `eval/scoring.go` now ranks by `Score` desc via a **stable** sort (`byScoreDesc`) before windowing/MRR, so an all-zero (legacy `/query`) result set is left in arrival order, keeping old behavior intact. `QueryData` tombstone-filters chunks by `reference_id` (mirrors `filterTombstonedRefs`); `include_chunk_content` is set (the `/query/data` analogue of the #21 `include_references` lesson). Boy-scout: the self-referential seed (`eval-seed-score-from-rank`) + golden case (`query-score-from-rank`) that asserted "Score remains 0" were updated to the new decision so `make eval` stays green. `/queries` and `/queries:describe` unchanged (still map Score 0); reranker/hybrid-weighting stays out of scope - this only provides the before/after metric it needs. If upstream later adds a per-chunk score field, switch the mapper to read it (confirm the key against that version first - do not invent it).
- 2026-06-23 Issue #49: added the code-graph retrieval-quality eval harness, mirroring #41 for the `/code/*` surface. New `eval/codegraph/` package (`package cgeval`): a synthetic fixture `seed/*.json` (one `codegraph.GraphPush` minus `repo`, spanning calls/defines/imports/depends_on/value_ref) pushed via `/code-graph:bulk`, `golden/*.json` cases keyed by `kind` (one per `/code/*` endpoint), both `go:embed`-ed; plus `cmd/codegraph-eval` and `make codegraph-eval` (same opt-in contract as `make eval`). Two decisions: (1) **synthetic** fixture, not a real-repo extraction snapshot - the design note floated snapshot-seeding (would double as an analyzer-quality regression guard) but the issue scope is measurement-only + CI-reproducible-without-a-corpus, so synthetic ships now and snapshot-seeding is a separately-scoped follow-up (noted in ROADMAP). (2) **dual scoring**: ranked recall@k/MRR for `search`/`path` (ordered), set precision/recall/F1 for the deterministic traversals (the CTE `ORDER BY id,depth` walks) - a phantom-node/over-walk regression is a precision drop that rank-only recall hides. `expected`/result keys match by case-insensitive EXACT equality on the canonical entity ID (or `from->to` edge key), NOT substring like the memory eval, because substring would let one ID count as relevant when contained in another and corrupt set precision. Aggregate mean recall@k is the gate (exit non-zero below floor). Lands independently of #48 (code surface already ranks by match class / degree).
- 2026-06-16 Issue #41: added a retrieval-quality eval harness (golden set + `cmd/eval`, `make eval`). New `eval/` package: versioned `seed/*.json` corpus (real platform memories) + `golden/*.json` cases (`{name,query,mode,top_k,expected}`), both `go:embed`-ed so the binary is self-contained; loaders validate + dedup; `cmd/eval` bulk-ingests the seed via `/memories:bulk`, waits for the job, queries each case, and computes recall@k + MRR. Opt-in like the integration suite (needs `MEMORY_BASE_URL`/`MEMORY_TOKEN`), NOT part of `make test`. This delivers only the measurement layer; reranker/ranking work stays out of scope (now unblocked).

- 2026-06-08 (0.2.3) Async ingest path never persisted item payload: `ingest_jobs`
  /`ingest_job_items` (0001) stored only the idempotency key - `CreateJob` didn't
  write `Text`/`Metadata`, `ClaimNextItem` didn't return them - so the worker sent
  EMPTY text to LightRAG and every insert 422'd `string_too_short` (3278 items
  failed on the cluster). Masked until the worker actually ran (the 0.2.2 wiring
  fix); `MemStore` keeps the full item so unit tests passed, and the PG
  integration test built an item with Text but never asserted it round-tripped.
  Fix: migration 0002 adds `text`/`metadata` (jsonb) columns; `CreateJob` persists
  them; `ClaimNextItem` returns them; PG round-trip test now asserts the payload
  survives. Lesson: two independent latent bugs in the same never-exercised path
  (worker wiring, then payload persistence) - end-to-end smoke would have caught
  both; unit tests with the in-memory store caught neither.
- 2026-06-08 (0.2.2) Ingest worker `Pool` was created + `Start()`ed but NEVER
  wired to job creation: `Pool.Notify` had a single caller (inside `Pool.Resume`)
  and `Resume` had ZERO callers, so the bulk handler made `queued` jobs and
  nothing ever woke a worker - every `ingest_jobs` row sat `queued` forever (no
  repo reached Ingested). First surfaced on the dogfood E3 ingest; the bulk path
  had never run end-to-end (cf the 2026-06-06 "ingest_jobs un-migrated latent
  gap" note - same blind spot). Fix: `Enqueuer` takes a `Notifier` (the Pool) as
  a REQUIRED arg and notifies after persist (required so the wiring can't go
  silently missing again); `app.go` calls `Pool.Resume` at startup;
  `ListRunningJobs` -> `ListUnfinishedJobs` (`status IN queued/running`) so a
  restart recovers stranded jobs without DB surgery; `Resume` schedules via a
  blocking stop/ctx-aware send, not the lossy fast-path `Notify`, so recovery
  never drops a job when unfinished > notify buffer. KNOWN follow-ups (pre-
  existing, NOT triggered by the single-notify-per-job invariant, see ROADMAP):
  `runJob` Done/Failed counter is a non-atomic read-modify-write that would race
  on a double-notify; a crash mid-item leaves items `running` and `ClaimNextItem`
  only claims `pending`, so resume drains to a wrong count; ingester chunk-poll /
  `CreateMemory` has no timeout.
- 2026-06-08 (0.2.1) `/code-graph:bulk` Push() rejected fileless entities:
  the entity-scope check required every `FilePath` to be in `p.Files`, but a
  `go_package` entity legitimately has no single owning file (`FilePath==""`).
  Surfaced on the first real dogfood ingest (400 `invalid push scope ...
  file_path "" not in files`). Spec already declares `file_path` may be `""`
  ("" for repo node), and the store handles it (file_path default '', PK
  `(repo,id)`, upsert-in-place, never errantly deleted). Fix: skip the
  membership check for empty FilePath (entities only; edge/symbol SrcFile checks
  stay strict - every edge/symbol carries a real file). Only `go_package` is
  fileless today (golang.go + golang_fallback.go).

- 2026-06-16 audit-r2 codegraph: empty-FilePath entities (repo/package-scoped, e.g. go_package) are NOT reclaimed by file-granular reconcile. Reconcile deletes only via DELETE WHERE file_path=$2 for each f in p.Files; an entity with file_path='' is only refreshed when re-pushed with the same ID (upsert). For stable IDs this is benign; renamed/removed repo-scoped entities orphan forever. Intentional trade-off: requiring a sentinel owning file would complicate extractor contract. If reclamation needed: add extractor-scoped DELETE WHERE file_path='' when push declares repo-root scope.

**Correction, same day:** the line originally here claimed this test was "empirically stable (0 flakes / 15 runs under `-race`)". That was true as far as it went but incomplete in a way that mattered: those 15 runs were all under `-race`, which perturbs goroutine scheduling enough to mask a real flake. The in-cluster review agent ran the package 3x without `-race` and got 3 failures, then `-run TestPGStore_CreateJob_DeadlineFiresMidInsertLoop -count=20` without `-race` and got **13 failures out of 20**, always on the rollback assertion. Root cause: the test read an `atomic.Bool` immediately after receiving from the `done` channel, but `database/sql`'s `Tx.awaitDone` goroutine (the thing that can perform the rollback instead of `CreateJob`'s own `defer`) runs on its own goroutine with no happens-before relationship to the `done` send - so sampling the flag right after `<-done` was a genuine data race on ordering, not a data race in the `-race`-detector sense (the accesses were atomic), and `-race`'s scheduling perturbation happened to almost always give the rollback goroutine enough of a head start to win. Fixed by having `fakeTx.Rollback` signal a buffered (capacity 1) channel instead of setting a flag, and having the test `select` on that channel with a 2s timeout after `<-done`, so it waits for the rollback event instead of sampling for it. Lesson: a goroutine spawned by a stdlib package you don't control (here, `database/sql`'s own `Tx.awaitDone`) is exactly as capable of introducing an ordering race as a goroutine you wrote yourself, and `-race` is a detector for concurrent memory access, not a guarantee about event ordering - it will not reliably catch "I assumed A happens-before B but nothing enforces that."

**WriteTimeout does NOT bound a handler - corrected after review caught the file describing it as one.** `net/http/server.go`'s entire `WriteTimeout` implementation is `defer func() { c.rwc.SetWriteDeadline(time.Now().Add(d)) }()`, armed on the raw connection right after headers are read, BEFORE the handler runs. It does not cancel `r.Context()`, does not abort a parked handler, does not close the connection while the handler is running, and emits no HTTP status - it only makes the eventual response write fail once the deadline has passed. Had `WriteTimeout` been set before #85/#86, the 18 hung requests would have behaved identically server-side (same 300s park, same held pool slot, same zero log lines); it provides zero protection against this hang class, full stop. It is now documented everywhere (app.go, values.yaml, this entry) as only a best-effort backstop against a response write that genuinely never completes (e.g. a client that stops reading).

**Consequence: a naive server-wide `WriteTimeout` creates retry amplification on `/code-graph:bulk`.** That route's single `Reconcile` transaction legitimately runs 50-194s+; since `WriteTimeout` cannot abort the handler, a run that finishes just past the deadline commits successfully in Postgres and then loses its response (client sees `EOF`, not a truncated body), so `tatara-memory-repo-ingester`'s `doWithRetry` (maxRetries=2) retries an already-successful push up to twice more - exactly the pool-pressure pattern this whole fix exists to prevent. **Non-obvious pitfall found while proving the exemption actually works:** the naive version of this fix compiled, passed `_ = ...`-swallowed error checks, and did *nothing* - `TestPostCodeGraph_SurvivesServerWriteTimeout` failed with a client-side EOF even though the server logged a normal 200. Embedding an interface only promotes the methods that interface itself declares (`Header`/`Write`/`WriteHeader`), never extra methods the underlying concrete value happens to have, so `ResponseController` hit a dead end at the outermost `statusRecorder` and silently returned `http.ErrNotSupported`, which the codegraph handler discarded via `_ =`. Fix: `statusRecorder` now implements `Unwrap() http.ResponseWriter`, letting `ResponseController` walk through all three layers to the real connection. Lesson: any `http.ResponseWriter` wrapper in this codebase must implement `Unwrap()` or it silently breaks `http.ResponseController` for every handler downstream of it - verify with an end-to-end test through the real middleware stack, not a direct call to the handler function, or this exact silent-no-op is invisible.

A LightRAG document delete is a synchronous knowledge-graph rebuild holding that lock for **6-42s** (41.85s measured, #90 Q9), so the budget was one to two orders of magnitude short. Fix: the busy retry now runs to a **deadline** (the caller's if it has one, else `defaultBusyRetryBudget` 45s) with exponential backoff capped at 2s, and exhaustion returns a typed `*lightrag.BusyError` that `wrapUpstream` maps to `ErrBusy`; without that explicit `errors.As` case a non-`HTTPError` falls through to `ErrUpstream` -> 502, which the ingest client treats as permanent.

**The non-obvious part, and why a bigger per-call budget alone is wrong:** LightRAG's delete is *asynchronous on its side* - `DELETE /documents/delete_document` returns `deletion_started` in milliseconds (observed 1.4ms-1.07s) and the 6-42s rebuild holds the lock **after** the call returns. The purge is serial over `reconcile_files`, so file N+1's delete meets a lock held by **our own** file-N delete, not only by a foreign insert wave. Per-call waiting therefore scales with the file count and would run a wide reconcile past any client timeout. So the budget is applied **once to the whole batch** (`memory.DefaultPurgeBudget`, `MEMORY_PURGE_BUDGET`, `memoryPurgeBudget`) and propagates into `DeleteDocs` as the ctx deadline. 45s is chosen from both ends: it covers one full measured lock hold (nothing is shed that waiting would have saved) and stays under `tatara-memory-repo-ingester`'s 60s HTTP client default, which the #85/#86 note in `values.yaml` already flags as the binding client-side bound. Overrunning it is honest backpressure: the completed files are already cleared from the source index, so the client's retry resumes on the remainder instead of restarting (boy-scout: `DeleteMemoriesBySources` also used to drop the partial count of the file that failed, under-reporting work already done).

**Not fixed here, deliberately:** the backpressure branch in `errmap.go` still logs nothing (that is #84), and nothing serialises insert vs purge on one LightRAG instance - with a lock held for the minutes an ~1,900-create insert wave takes (#91), a 45s budget still ends in a shed request. What changed is that it is shed after a real wait with durable progress, counted as a `delete_docs` error, instead of after 1.4s counted as a success. semver:patch (no REST contract change; one new optional env/values key).

**Reconciled against #97 on merge (2026-07-29):** this branch was written before `memory.ErrBusy` existed, when `ErrTransient` was the only non-permanent classification and was picked purely to escape the `ErrUpstream`/502 path. #97 then split the taxonomy and, in the same sweep, moved the single-response `delete returned status="busy"` envelope from `ErrTransient` to `ErrBusy` - see its own note below, which explicitly predicts the purge path's 503 -> 429. #97 could not touch `*lightrag.BusyError` because that type does not exist on `main`, so there is no double-classification, but leaving it on `ErrTransient` would have been actively incoherent: one busy response would return 429 while forty-five seconds of the same busy response returned 503, i.e. the longer the backpressure, the more it looked like an outage. `wrapUpstream` now maps `*lightrag.BusyError` to `ErrBusy`. An exhausted purge budget is backpressure, not unavailability - the caller should come back later, which is what 429 + `Retry-After` says, and both clients now honour it (tatara-memory-repo-ingester#32, tatara-operator#484). `ErrTransient`/503 stays reserved for a genuine server-side fault worth alerting on.

2026-07-29 (issues #79/#80/#82/#87) **`/memories:bulk` 503s under concurrent ingest: admission control + a real 429/503 split.** Four issues, one family, four rounds of bot RCA that partly contradicted each other (#79 "LightRAG-coupled backpressure, DB pool ruled out"; #82 "not LightRAG, shared-Postgres-pool starvation from long `/code-graph:bulk` transactions"; a later #82 comment "both mechanisms are live"; #87 recurrence with Postgres measured healthy at 44/100 conns). Re-verified against main before writing anything, and all three of the load-bearing claims held:

- **Shared pool, sized 10.** `openDB` hard-coded `SetMaxOpenConns(10)`/`SetMaxIdleConns(2)` on ONE `*sql.DB` handed to `ingest.PGStore`, `memory.TombstoneStore`/`SourceStore`, `codegraph.PGStore`, `codegraph` analytics, the ingest worker pool AND `/readyz`. With `WORKER_POOL_SIZE=4`, four workers alone could hold 4 of the 10.
- **`/code-graph:bulk` is one transaction for the whole push.** `codegraph.PGStore.Reconcile` opens a single `BeginTx` and holds it across every per-file DELETE and every insert - one connection pinned for the full 50-194s of a large repo's reconcile. Deliberately exempt from `WithCreateJobTimeout` and from the server `WriteTimeout`.
- **NO admission control anywhere.** The router's middleware chain was request-id -> logger -> recover -> access-log -> metrics -> auth. Nothing bounded concurrency on any route.
- **Everything retryable was a 503.** `errmap.go` mapped `memory.ErrTransient` AND `context.DeadlineExceeded` to `503 + Retry-After: 5`, so `/memories:bulk` saturation reported as a server error and lit the 5xx-ratio alert (`afq61w88eornke`) on every burst. #80's "429-vs-503 gap still unfixed" was accurate and still unfixed.

The #85/#86 fix (`WithCreateJobTimeout`, 2026-07-26) only converted the *shape* of the failure - unbounded park + 499 became fail-fast + 503. It bounded the symptom, never the load, which is why #87 kept re-firing through 2026-07-28 on a HEAD that already carried it.

**What shipped, as one design rather than four patches:**

1. **Admission control** (`internal/httpapi/admission.go`): a counting semaphore per bulk class with a bounded acquire wait, applied via `r.With(...)` to `/memories:bulk` (`memories_bulk`, default 4) and `/code-graph:bulk` (`code_graph_bulk`, default 2). Two separate budgets, deliberately: a shared one would let a code-graph wave consume every slot, which is the starvation being fixed. A request that cannot get a slot within `ADMISSION_WAIT` (5s) is shed; a client that disconnects while queued keeps the existing 499 path and is NOT counted as shed.
2. **The pool is now the stated budget.** `DB_MAX_OPEN_CONNS` (default 20, was a hard-coded 10) / `DB_MAX_IDLE_CONNS` (5, was 2), applied once in `newAppWithDeps` rather than in `openDB` so a single place owns them. `config.validate` REFUSES TO START when `memoriesBulkMaxInFlight + codeGraphBulkMaxInFlight + workerPoolSize >= dbMaxOpenConns`: a budget that can still drain the pool is a limiter that cannot do its job, and shipping one would look like a fix while behaving exactly like #82. Defaults 4+2+4=10 < 20. Raising the pool is supported by #87's own evidence - Postgres measured 44/100 connections during a shedding burst, so the binding constraint was this client-side cap, not the server.
3. **429 means backpressure, 503 means unavailable.** New `memory.ErrBusy` (upstream saturated: LightRAG delete `status="busy"`, an upstream HTTP 429, or a call that ran out of its time budget) maps with `context.DeadlineExceeded` to `429 + Retry-After`; `memory.ErrTransient` (upstream 5xx / unreachable / `context.Canceled`) keeps 503. Boy-scout: an upstream **HTTP 429 previously fell through `wrapUpstream`'s default branch to `ErrUpstream` -> 502**, turning an explicit "slow down" into a permanent failure.
4. **Shed load is visible.** `http_admission_total{class,result}`, `http_admission_in_flight{class}`, `http_admission_waiting{class}`, `http_admission_wait_seconds{class,result}`, a WARN `http.admission.shed` line per shed (request_id, class, route, waited_ms, retry_after_s), and a new `MemoryBulkAdmissionShedding` PrometheusRule - because moving shed load off 5xx also moves it out of sight of `MemoryHigh5xx`, and an invisible fix is a worse failure mode than a noisy alert.

**Retry-After is spread, not constant:** `base + base*{0,1/8,1/4,3/8}` selected round-robin from a fixed table. A constant value tells an entire shed wave to come back at the same instant (exactly #87's mass concurrent re-ingest), and the table-index form keeps the arithmetic in `int` so there is no counter-to-int conversion for gosec G115 to reject - the `uint64 % spread` version was flagged, and a `//nolint` would have been noise for something expressible cleanly.

**Client contract change - REQUIRES companion work in other repos (not done here, deliberately out of scope):** `tatara-memory-repo-ingester` and the operator's ingest client must treat **429 as retryable and honour `Retry-After`**. Anything that retries only on 5xx will now hard-fail on shed load where it used to retry a 503. The related client-side root cause (`tatara-memory-repo-ingester#31`: a whole repo's code graph pushed as one unbatched synchronous transaction) is what makes a single `/code-graph:bulk` hold a connection for 194s in the first place; admission control bounds its blast radius but does not shorten that transaction.

**Deliberately NOT touched** (owned by other issues): the LightRAG purge-path lock and retry budget (#90/#91), the CNPG primary outage (#83), and codegraph transaction chunking. Note that `busy` moving from `ErrTransient` to `ErrBusy` does change the purge path's status code (503 -> 429) even though its retry behaviour is untouched. semver:minor (REST contract change on an error path, plus new config).

**Reconciled against #97 and #93 on merge (2026-07-29), and the one thing worth knowing about this entry:** `logPurgeErr`'s predicate was written as `errors.Is(err, ErrTransient)` when `ErrTransient` was the only non-permanent classification and carried LightRAG's `delete status="busy"`. #97 then split the taxonomy - `ErrBusy` (saturated, 429 + `Retry-After`) vs `ErrTransient` (genuinely unavailable, 5xx/unreachable, 503) - and moved `busy` to `ErrBusy`; #93 added `*lightrag.BusyError` on the same side. Porting the old predicate across unchanged would have **inverted this fix's intent exactly**: the one failure class that is routine under load (a held pipeline lock, the very thing #84 was raised about) would have logged ERROR, while a real LightRAG outage on the purge path would have been muted to WARN. The predicate is now `errors.Is(err, ErrBusy) || errors.Is(err, context.DeadlineExceeded)` - deliberately the same condition as `mapServiceError`'s backpressure branch, so the log level always agrees with the status the caller was handed (WARN iff 429). The bare-deadline arm is not redundant: #93's whole-batch purge budget can expire inside `sources.TrackIDs`/`DeleteByFile`, whose store errors never pass through `wrapUpstream` and so are never reclassified as `ErrBusy`. `TestDeleteMemoriesBySource_TransientDeleteFailure_LogsWarn` was renamed to `..._BusyDeleteFailure_LogsWarn` and now asserts `ErrBusy` - an intentional change of what the test means, not a mechanical fixup - and a new `..._UpstreamUnavailable_LogsError` (upstream 502) pins the other half so the predicate cannot silently drift back. `DeleteMemoriesBySources`'s failure line keeps #93's `memory.delete_by_sources.incomplete` message, its `total_purged` = `total + n` partial count and its `files_count` field, but is now emitted through `logPurgeErr` rather than an unconditional `WarnContext`, so both changes survive intact.
2026-07-29 (issue #89) **Analytics recompute held a Postgres backend across N sequential LLM calls; the "~5 leaked per recompute" framing is wrong.** The issue reports `mem-mtg-pg` backends owned by `tatara_memory` growing 4 -> 87 over 5.5h and never terminating (SQLSTATE 53300, all 97 non-superuser slots held), correlated at ~4.9 per `analytics recompute`, and calls it a connection leak. **Audited every acquisition on that path and there is no missing release:** `RecomputeAnalytics`'s four acquisitions (the `reconciled_at` snapshot `QueryRowContext`, `loadEntityIDs`, `loadEdgePairs`, and the `BeginTx`) each release on every Go-level path - `QueryRow.Scan` closes its rows, both loaders `defer rows.Close()`, the tx has `defer tx.Rollback()` since before this issue, and `recompute` runs in a goroutine with no recover so a panic would take the process down rather than orphan a connection. A new table-driven test fails each of the nine statements in turn plus a mid-labelling context cancellation and asserts the pool slot comes back every time (`analytics_conn_test.go`); all nine passed *before* any fix. So ~4.9 is not "leaked per run" - it is almost exactly the number of distinct pool acquisitions one run makes, which is what you would expect if backends are orphaned server-side (the issue's own favoured mechanism (a)) rather than lost client-side.

**What was actually wrong, and is now fixed:** `RecomputeAnalytics` opened its transaction and *then* called `labelCommunity` once per community inside it (`analytics_store.go:128-136` pre-fix), and `labelCommunity` is an outbound OpenAI HTTP call.
